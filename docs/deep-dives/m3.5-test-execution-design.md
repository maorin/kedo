## 背景

M3 浏览器写控制完成后，2026-05-09 实战让 ReactAgent **生成**了 14 模块云桌面（天华星航 V5.00）的测试用例文档：

```
~/test/test/
├── 01-login.md                  (登录测试)
├── 02-overview.md               (概览)
├── 03-desktop-management.md
├── ...
├── 14-physical-machine-monitoring.md
└── README.md
```

每个 `.md` 含 5-10 个 TC，结构是：

```markdown
## TC-DM-001 桌面列表加载
| 项目 | 内容 |
|---|---|
| 优先级 | P0 |
| 前置条件 | 用户已登录，具备桌面管理权限 |
| 测试步骤 | 1. 点击左侧菜单【桌面管理】 |
| 预期结果 | 页面加载桌面列表，显示桌面名称、状态、IP、所属用户、操作按钮等字段 |
```

**总计约 70 个 TC**。M3.5 的目标是把这些**自动执行**——不只是生成文档而是真跑测试，输出 PASS/FAIL 报告 + 失败截图。

## 上次为什么 park

2026-05-09 试了**路径 A：纯 ReactAgent prompt 驱动**——给 agent 一个 task 让它读 md 自己跑。失败原因：

- agent 把 14 md 全读进 context → context 涨得很快
- 14 模块 × 5 TC ≈ 70 个 TC，单 task 跑完成本太高
- 收敛检测（M1 加的同 tool 同 fingerprint 3 次自动 pause）在探索类操作上误伤
- LLM "走捷径"倾向：跑几个 TC 后开始虚构结果不真点

决定：M3.5 重启时不再走路径 A，直接做**路径 B：写专用 `run_test_cases` 工具**，让执行链路**确定化**，不依赖 LLM 的耐心和细致。

## 核心设计矛盾

LLM 擅长**模糊推理**（写 TC 文档、总结结果），不擅长**确定执行**（同一 TC 跑 100 次给同结果）。测试自动化的本质需求是**确定性**（CI 同代码 → 同结果），把 LLM 塞进执行循环是反方向的。

所以 M3.5 的 Python 工具应该**尽量把 LLM 排除在执行链路外**。LLM 的判断成本（如果有）应该提前到"准备阶段"，到执行时纯机械。

但下面 5 个点都不是纯机械能解决的：

---

## 设计点 1：步骤 → 浏览器动作的映射

TC 里写 "点击【创建桌面】按钮" 要变成 `browser_click(text_match="创建桌面")`。谁做这个翻译？

### 方案 A — 纯 regex 模式

Python 写一组正则覆盖标准 LLM 措辞：

```python
PATTERNS = [
    (r"点击【(.+?)】按钮?",       lambda m: ("click", {"text_match": m.group(1)})),
    (r"点击【(.+?)】",             lambda m: ("click", {"text_match": m.group(1)})),
    (r"输入(?:用户名)?[\"'](.+?)[\"']", lambda m: ("type", {"value": m.group(1)})),
    (r"导航(?:至)?\s*[\"'](.+?)[\"']", lambda m: ("navigate", {"url": m.group(1)})),
    (r"等待(?:加载完成|页面加载)",   lambda m: ("wait_for", {...})),
    ...
]
```

- ✅ 完全确定性、CI 友好、cold start 快
- ❌ 脆——LLM 每次写步骤格式稍变就匹配不上，标 `UNSUPPORTED_STEP` 失败
- ❌ 真实场景 LLM 写步骤极多样（"按一下确定"/"敲回车"/"提交表单"）

### 方案 B — LLM 每步翻译

每个 step 调一次小 LLM（cheap model 如 Kimi/Haiku），把自然语言转成 `{action, params}`：

- ✅ 灵活，应对任何措辞
- ❌ 慢：70 TC × 平均 5 step = 350 次 LLM 调用，加上重试就是几千个 token 几十秒
- ❌ 不稳：同一步骤跑 10 次可能产生不同 JSON
- ❌ 把 LLM 塞回执行循环，违背 M3.5 初衷

### 方案 C — 写时就结构化（推荐方向）

改 M3 让 agent **生成 TC 时同时输出 `TC.json`**：

```json
{
  "id": "TC-DM-001",
  "title": "桌面列表加载",
  "priority": "P0",
  "preconditions": ["用户已登录"],
  "steps": [
    {
      "natural": "点击左侧菜单【桌面管理】",
      "action": "click",
      "params": {"text_match": "桌面管理"}
    }
  ],
  "assertions": [
    {"type": "element_exists", "selector": ".vm-row"},
    {"type": "text_contains", "in": ".page-title", "text": "桌面管理"}
  ]
}
```

- ✅ 执行期纯确定，run_test_cases 只读 JSON
- ✅ LLM 判断在生成期一次性完成
- ❌ 要改 M3 prompt 让 LLM 同时输出 md + json
- ❌ 老的 14 个 md 已生成，要补 json（半天工作）

### 方案 AC 混合

v1 用 A 跑通流程；同时改 M3 prompt 让以后生成的 TC 带 json。老的 14 md 让 A 凑合，新生成的走 C。两手准备，工作量稍多。

## 设计点 2：断言精度

"预期结果：列表中新增对应记录" 怎么验证？

| 级别 | 含义 | 实现 | 覆盖率 |
|---|---|---|---|
| **粗略** | 步骤跑完不报错就 PASS | 不验证预期结果，只看 click/type/navigate 没失败 | 60% TC，false positive 多 |
| **中等** | regex 抽预期结果里关键字 + 验证 | 跑完 `browser_query(text_match="新增") `检查存在 | 50% TC |
| **细致** | 结构化 assertion schema | TC 必须写 `assertions: [{type, params}]`，schema 严格 | 90% TC 但要训练 LLM 用 schema 写 TC |

粗略 v1 够用：测试目的是 catch obvious regression，而不是验证一切。

---

## 设计点 3：case 之间隔离

TC-A 改了页面状态（新建了个桌面），TC-B 从哪个状态开始？

- **简单**：每 TC 跑前 `browser_navigate(base_url)` 强制回到首页。状态可能没完全清，但简单。
- **中等**：跑前关掉所有 modal/弹窗，回首页
- **复杂**：每 TC 一个 incognito tab / 一个新 context

v1 简单即可。CI 化后再升级。

---

## 设计点 4：登录态怎么办

M3 密码硬规则（`<input type=password>` 永远拒）→ TC-LOGIN-* 类自动跑不了。

- **v1**：tool 自动跳过 `TC-LOGIN-` 前缀的 case，结果标 `SKIPPED  reason=password_field_blocked`
- **未来**：M5 credentials vault（专用工具走密码字段，跟普通 `browser_type` 隔离）

---

## 设计点 5：工具与 ReactAgent 的集成方式

### 方案 1：Python 直调 bridge

`run_test_cases` 内部直接 `await bridge.send_command(...)`，**绕过 ReactAgent**：

- ✅ 最快、确定性最强
- ✅ 70 TC 是 1 个 task 的 1 个 tool call，task token 消耗只有一次
- ⚠ Dashboard 进度看不到细节——需通过 `event_bus.emit("test_case_completed", ...)` 推自定义事件

### 方案 2：走 ReactAgent 每步一 tool call

让 LLM 自己 click → query → 验证：

- ✅ Dashboard 进度可视化细致
- ❌ 慢 N 倍
- ❌ LLM 可能在第 30 个 TC 时"走神"

倾向 1，加 event_bus 推 per-case 进度即可。

## 推荐的 v1 形态

```python
@tool
async def run_test_cases(
    md_file: str,                    # 单个 md
    tc_id: str = "all",              # "all" / "TC-DM-001" / "TC-DM-*"
    base_url: str | None = None,     # 每个 case 跑前先 navigate
    skip_password_cases: bool = True,
    output_dir: str | None = None,   # 默认 ~/test/test/results/
) -> ToolResult
```

返回：

```json
{
  "summary": {"total": 8, "passed": 5, "failed": 2, "skipped": 1, "duration_ms": 45230},
  "results": [
    {"tc_id": "TC-DM-001", "status": "passed", "duration_ms": 4250},
    {"tc_id": "TC-DM-002", "status": "failed", "failed_step": 3, "error": "ELEMENT_NOT_FOUND: 创建桌面",
     "screenshot": "~/test/test/results/screenshots/TC-DM-002.png"},
    {"tc_id": "TC-LOGIN-001", "status": "skipped", "reason": "password_field_blocked"}
  ],
  "report_md_path": "~/test/test/results/<md_basename>-results.md"
}
```

**实现路径**：

1. **regex 解析 md**：`^## TC-(\w+)-(\d+) (.+)$` 找 case 边界，提取测试步骤段 + 预期结果段
2. **步骤 → 动作**纯 regex 映射（v1 覆盖标准格式 60-70%）；不匹配标 `UNSUPPORTED_STEP` 整个 TC FAIL
3. **断言** v1 用粗略级（步骤无错即 PASS），不验证预期结果（false positive 可接受）
4. **TC-LOGIN-** 自动 skip
5. **每 case** event_bus 推 `test_case_completed` 事件给 dashboard 实时显示
6. **失败截图** → `results/screenshots/<TC-ID>.png`
7. **报告**：markdown 表格 + JSON 结构两份落盘

**工作量**：约 1 天。覆盖能跑 60-70% TC，剩下的标 unsupported 慢慢补。

## 演化路径（v2 / v3）

| 版本 | 改动 | 触发条件 |
|---|---|---|
| v1 | 上面 | 现在 |
| v1.1 | 补 step pattern 库（多语言、多措辞） | regex unsupported 率超过 30% |
| v2 | 改 M3 prompt 让 LLM 生成 TC.json（方案 C） | v1 unsupported 太多手工补不过来 |
| v2.1 | 断言精度从粗略升中等 | false positive 多到不可信 |
| v3 | 跑出来的 results.md 给 Reviewer 二审 | 想让 Reviewer 评测试覆盖完整性 |
| v4 | run_test_cases 改成 sub-agent 范式 | Step 翻译复杂到 regex 不够，但又不想每步阻塞主 agent |
